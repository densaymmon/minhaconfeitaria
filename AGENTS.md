## Application rules
- Ingredient costs use precise package price/quantity and explicit recipe units through the shared pure conversion module; legacy numeric projections remain for compatibility, and database triggers validate dimensions and flag affected recipes without touching order snapshots.
- Keep private pages under the authenticated layout and prefill TanStack Query caches in loaders; private reads remain scoped by database RLS.
- Save orders and recipe ingredients through transactional, invoker-security database RPCs; partial saves must never delete previous items.
- Preserve order item cost snapshots when ingredient prices change; historical profitability must not change with current supplier prices.
- Multi-bakery model: each bakery is identified by its owner account id (tenant = `user_id`). Team members (`equipe_membros`, roles `gerente`/`producao`, migration 0043) work inside the owner's bakery, so tenant code must use `public._tenant()` (owner id for members, own id otherwise) instead of `auth.uid()`: RLS policies (`(SELECT public._tenant()) = user_id`), `user_id DEFAULT public._tenant()` and every SECURITY DEFINER RPC (use `public._tenant_financeiro()` in money operations, which blocks the `producao` role). Keep `auth.uid()` only where the person matters (platform admin, terms, team management). The `producao` role is also blocked by RESTRICTIVE `papel_financeiro`/`papel_altera_*` policies; in the app gate pages with `paginaPermitidaAoPapel`. File uploads go to the bakery folder (`confeitaria.user_id`/`meuPapelQ.confeitaria_id`), never `user.id`. Every table keeps tenant RLS and every SECURITY DEFINER RPC must filter every row it reads or writes by the tenant; `tests/db/multiempresa-isolation-smoke.sql` and `tests/db/equipe-smoke.sql` must keep passing. Bakery profile lives in `public.confeitarias` (one row per owner, created by the `trg_criar_confeitaria` trigger). New signups are gated by `public.plataforma_config.cadastro_aberto` (closed by default; only admins change it). Enforce relationship ownership in the database; frontend checks are not security boundaries.
- Never hardcode a bakery's name, slogan or Pix key in the code; read them from `confeitarias`/`configuracoes`.
- Public catalog (`/c/$slug`, `/pedido/$codigo`): anonymous visitors never read tables. They only call `catalogo_publico`, `criar_pedido_catalogo`, `acompanhar_pedido_catalogo` and `informar_pagamento_catalogo` (SECURITY DEFINER). Prices, delivery fee and item cost snapshots are computed on the server; never trust values sent by the browser, never return cost, recipe, margin or other customers' data. `tests/db/catalogo-smoke.sql` must keep passing.
- Short public links: catalog at `/$slug` (also `/c/$slug`) and order tracking at `/p/$codigo` (10-char `pedidos.codigo_curto`; `/pedido/<uuid>` keeps working). Any new top-level page path must be added to both `public._slug_reservado()` and `SLUGS_RESERVADOS` in `src/lib/catalogo.ts`.
- Product variations live in `produtos.opcoes` (validated by `_opcoes_validas`); catalog orders send `opcoes` per item and `_aplicar_opcoes` computes price, cost and description on the server. Never expose option `custo` publicly.
- Platform access: `confeitarias.acesso` (`pendente`/`ativo`/`bloqueado`) is enforced in the database by the RESTRICTIVE policy `acesso_liberado` (`_acesso_liberado()`) on every table that has `user_id`. Any new tenant table must get that policy too; `tests/db/plataforma-smoke.sql` fails otherwise. Owners update `confeitarias` only through column grants: add new owner-editable columns to the `GRANT INSERT/UPDATE (...)` list; never grant `acesso` or `termos_*`. Platform admins are login-only accounts (no `confeitarias` row) whose e-mail is in `plataforma_admin_emails`; they use the separate admin site in `admin/` (static Vite app on GitHub Pages, own Supabase session) and every admin RPC checks `_eh_admin()`. Never put platform administration back inside the bakery app. New accounts follow `plataforma_config.cadastro_aberto`/`aprovacao_manual`. Bump `TERMOS_VERSAO` in `src/lib/termos.ts` when the terms change materially.
- Plans and subscriptions: `planos` (price, limits, `recursos` among custos/estoque/financeiro/recorrentes/catalogo/ia) and `assinaturas` (teste/ativa/cortesia/cancelada; effective status via `_situacao_assinatura` adds atrasada/suspensa after `plataforma_config.dias_tolerancia`). Suspended or cancelled subscriptions are blocked by `_acesso_liberado()`; the catalog requires `_catalogo_liberado()`; product and monthly order limits are enforced by triggers (`PLANO:` errors). In the app, gate pages with `recursoDaPagina` and sections with `useRecurso`/`RecursoBloqueado`. Subscription tables (`assinaturas`, `assinatura_pagamentos`, `plataforma_contas`) are readable by the owner but written only by admin RPCs.
- Performance: the QueryClient caches for 60s (`staleTime`) and the router preloads on intent with a pending skeleton; never put writes inside a `queryFn` (the daily "em produção" transition runs in `avancarPedidosDoDia`); the authenticated layout reads the session locally (`getSession`). For quick actions on orders use `otimista`/`alterarPedido`/`alterarItem` from `src/lib/cache-pedidos.ts` (update the cache, write, roll back on error) instead of awaiting a full refetch.
- Catalog extras (0041): agenda (`dias_fechados`, `datas_bloqueadas`, `horarios_retirada`), brand `cor_primaria`/`logo_url`, delivery fee per neighbourhood (`taxas_bairro`), coupons (`cupons`, validated only on the server by `_desconto_cupom`; anonymous visitors preview with `validar_cupom_catalogo` and never read the table) and custom orders (`criar_encomenda_catalogo`, reference photos uploaded anonymously to `catalogo/encomendas/<slug>/` only when `aceita_encomenda`; the order is created without items, `encomenda = true`, and the tracking page shows "aguardando orçamento" while it has no items). `tests/db/catalogo-extras-smoke.sql` must keep passing.
- Catalog sales (0044): `produtos.limite_dia` (units per delivery day, all origins, enforced in `criar_pedido_catalogo`), sale window `venda_de`/`venda_ate` (seasonal), kits in `produtos.componentes` (validated by `_validar_componentes`, one level; cost = `_custo_base_produto` + components, the ingredient list expands kits; stock consumption of kits is not automatic), deposit `confeitarias.sinal_percentual`/`sinal_a_partir_de` (stored in `pedidos.sinal_valor`), loyalty `fidelidade_*` (every N non-cancelled orders of a phone, the next catalog order gets the discount, never stacked with a coupon) and reviews (`avaliacoes`, written only by `avaliar_pedido` after delivery; owners can only toggle `publicada`). Catalog functions are patched with checked string replacements marked `/*0044*/`. `tests/db/vendas-smoke.sql` must keep passing.
- Management (0045): `historico` is written only by triggers (`_historico_pedido`, `_historico_pagamento`, `_historico_preco`, author from `_autor_historico`: owner, team member name/e-mail, catalog customer or system) and is readable by owner/manager only; `confeitarias.meta_vendas_mes`, `produtos.validade_dias` and `insumos.alergenos` feed the monthly goal and the printable labels. Pure rules for the week agenda, shopping list, delivery route, cash flow, goal and labels live in `src/lib/gestao.ts`. `tests/db/historico-smoke.sql` must keep passing.
- Platform (0046): `admin_metricas` (usage per bakery, signups per month; churn-risk rule `riscoDeCancelamento` in `src/lib/plataforma.ts`) and error monitoring: browsers report screen errors through `registrar_erro` (anon allowed, deduplicated per hour, capped at 200 new rows/hour, kept 30 days; client in `src/lib/monitor-erros.ts`, wired in `__root.tsx` and `admin/src/main.tsx`); `erros_app` is read only through `admin_listar_erros`. New bakeries see the "Primeiros passos" checklist (`src/lib/primeiros-passos.ts`) on Hoje. `tests/db/plataforma-uso-smoke.sql` must keep passing.
- Push notifications (0042): the app is a PWA (`public/manifest.webmanifest`, `public/sw.js` without page caching). Devices subscribe through `salvar_inscricao_push` (`push_inscricoes`, owner RLS); the VAPID private key lives only in `plataforma_segredos` (service role only, never in the repo; the public key is `VAPID_PUBLICA` in `src/lib/push-cliente.ts`). `avisarPedidoNovo` (server function, `src/lib/push.functions.ts`) is called by the catalog after an order and sends at most one push per order (claims `pedidos.push_avisado_em`, only for catalog orders created in the last 10 minutes); encryption/VAPID are in `src/lib/web-push.ts` (WebCrypto, RFC 8291 test vector in `web-push.test.ts`). Only known push service hosts are contacted. `tests/db/push-smoke.sql` must keep passing.
- Order payments: once an order has rows in `pedido_pagamentos`, `valor_entrada`/`saldo_quitado` change only through `registrar_recebimento_pedido`/`editar_recebimento_pedido`; `salvar_pedido` preserves them (migration 0047, `tests/db/salvar-pedido-recebimentos-smoke.sql` must keep passing).
- Plan features must also be enforced on the server: server functions that cost money (AI) call `minha_assinatura` and use `podeUsarRecurso` from `src/lib/assinatura.ts`; hiding the button in the UI is not enough.
- Product photos/videos live in `produto_midias` (max 10, saved through `salvar_midias_produto`, first photo = `produtos.imagem_url` cover); files go to the `catalogo` bucket under `<user_id>/`.
- "Mais" menu: the links live in one place, `src/lib/navegacao.ts` (`GRUPOS_MENU`, `linksMais`, `linksCompras`, `gruposDoMenu(papel)`), used by both the layout drawer (`_authenticated/route.tsx`) and the `/mais` page. Add new screens there, inside a group; never copy the list into a screen. Role filtering stays in `paginaPermitidaAoPapel`; `src/lib/navegacao.test.ts` must keep passing (no screen may disappear, no duplicates, no link without a route).

- Expose read-only MCP tools through the SDK TanStack plugin with OAuth caller tokens and a shared RLS client; agents must never bypass owner isolation.
- Preserve canonical same-origin OAuth consent return paths through login and signup so external authorization can complete safely.

- Interpret order messages through an authenticated server function with strict structured output and server-scoped product matching; apply only after review and save through the existing transactional order RPC.
